# Restaurants in four languages (i18n): design

Date: 2026-11-17. Status: design for approval, not implemented.
Branch it was written on: `codex/restaurantes-ux` (local only).
Mockup: `scratchpad/features/i18n.html` (desktop and 390 px phone side by side).

Portuguese (pt-PT), English, Spanish and French for the whole **restaurant** side of SeatPlan:
discovery, the public restaurant page, the booking flow, the manage page, the diner emails,
the staff pages and the owner pages. No new dependency: a tiny typed i18n layer of our own,
built on the browser's `Intl` and, on the server, plain Python dictionaries.

**English stays the default and the fallback**, so every existing test that asserts English text
keeps passing unchanged. The events vertical never changes and is always shown in English, even
when the person picked another language on a restaurant page.

## 2. Goal and user stories

**Goal.** Anyone can find, book and manage a table, and every restaurant can run its service, in
Portuguese, English, Spanish or French, with the emails in the language the diner booked in. The
language is detected once, can be changed in one tap, and is remembered on that browser.

### Diner
1. As a diner in Lisbon whose phone is set to Portuguese, I open SeatPlan and everything on the
   restaurant pages is in Portuguese without me doing anything.
2. As a Spanish tourist, I can switch the language to Español from the header on any restaurant
   page, and it stays Español when I come back tomorrow on the same phone.
3. As a diner who booked in French, my confirmation, change, reminder and cancellation emails,
   the calendar invite, and the manage page opened from the email are in French, even if I open
   the link on my partner's laptop.
4. As a diner, dates, times, numbers and plurals read naturally ("sexta-feira, 21 de novembro",
   "20:00", "8,4", "1 pessoa / 2 pessoas", "0 personne" in French).
5. As a diner who reads the email in another language than the site, I can say on the manage page
   which language future emails about this booking should use.

### Staff
6. As a waiter at a Lisbon restaurant, I run the floor in Portuguese while the owner uses English
   on the same account on another device (the choice is per browser).
7. As staff, I see in which language a booking was made ("Booked in Español"), so I can greet the
   party in the right language. Emails I trigger by moving or cancelling a booking go out in the
   **diner's** language, never mine.

### Owner
8. As an owner, I set up the restaurant (profile, photos, hours, review and publish) in my language.
9. As an owner, my listing is usable by tourists without me translating anything: everything the
   platform writes (labels, hours, features, ambience sentences, emails) is translated; only the
   text I typed myself (description, view text, review replies) stays as I wrote it.

## 3. Non-goals

- **Events stay untouched and English**: no edits to `frontend/src/pages/events/`, `editor/`,
  `join/`, `account/`, `backend/app/events_service/`, `routers/events.py`, `attendee.py`,
  `guest_*.py`, `visitor.py`. The shared modules this spec touches (`design/components`,
  `api/client.ts`, `main.tsx`, `core/errors.py`, `main.py`, `models.py`, `mail/`) keep event output
  byte-for-byte identical (tests in section 11 prove it).
- **No machine translation** of text people type: restaurant names, descriptions, view text
  ("Tagus river"), review comments, notes, room and table names stay as typed.
- **Guest account code emails** (sign-in codes, password reset) stay English: they are sent by
  `routers/guest_accounts.py`, which belongs to events.
- **Room editor** (`frontend/src/pages/room-editor/`) is not migrated in this work: Sergio is
  actively editing it. Its strings stay English until a phase 5 agreed with him (section 14). The
  owner side menu around it (`OwnerShell`) is translated, so the page is mixed-language until then.
- **No locale in the URL path** (`/pt/restaurants/...`): see section 4.3 and decision D1.
- **No SEO work** (hreflang, server-side rendering). The site is a client-rendered SPA on Vercel.
- **No right-to-left languages**, no Brazilian Portuguese wording (pt-BR browsers get pt-PT).
- **No translation provider/API** (DeepL, Google Translate). Catalogues are static files in the
  repository, reviewed by people. If Martim later wants owner descriptions machine-translated,
  that is a separate feature behind a provider interface.
- The `/demo` home page and the organiser login (`/login` without `next=/owner`) stay English.

## 4. Behaviour

### 4.1 Which language a page uses

Pure function `pickLocale` (`frontend/src/i18n/detect.ts`), first match wins:

1. `?lang=xx` in the URL, when `xx` is a released locale (section 13). It is kept **for this tab
   only** in `sessionStorage["seatplan:lang:tab"]` (never in `localStorage`: the link may be opened
   on someone else's laptop, story 3, and must not change that person's language for good) and then
   removed from the address bar with `navigate({ pathname, search: <search without lang>, hash },
   { replace: true })`. Every other query parameter (`date`, `time`, `party` of the waitlist offer
   link, `next` of `/login`) is kept. The strip runs once per location key, so React StrictMode's
   double effect cannot loop.
2. The tab choice from step 1 (`sessionStorage["seatplan:lang:tab"]`).
3. The saved choice: `localStorage["seatplan:lang"]`, written **only** when the person picks a
   language in the picker (which also clears the tab choice). Never written from detection or
   from a link.
4. The browser's languages: `navigator.languages`, matched by primary subtag:
   `pt-BR` -> `pt`, `fr-CA` -> `fr`, `es-419` -> `es`.
5. `en`.

Every step only accepts a **released** locale (section 13); an unreleased saved or tab value is
ignored, not deleted.

Events routes ignore all of this: the provider computes
`effective = isRestaurantRoute(pathname, search) ? picked : "en"`, using the existing function
in `PageShell.tsx`. So an events page is English even right after the diner picked Português.

The provider writes `document.documentElement.lang` (`pt-PT`, `es-ES`, `fr-FR`, `en-GB`... and
plain `en` on events routes, as `index.html` has today) so screen readers pronounce the page
correctly.

### 4.2 Which language an email uses

Each booking and waitlist entry stores the language it was made in (`bookings.lang`,
`waitlist_entries.lang`). Server rule, pure function `booking_language(body_lang)`
in `backend/app/restaurant_service/language.py`:

1. `lang` in the request body (the frontend always sends its **effective** locale, which is `en`
   until a language is released);
2. else `en`.

The `Accept-Language` header is **deliberately not used**. Reason: during the deploy of phase 3,
browser tabs still running the old bundle send no `lang`; with a header fallback a Portuguese
browser would get Portuguese emails from an English site, and before Martim released `pt` (with
unreviewed words). A missing `lang` therefore means exactly what it meant before: English.

Every email about that booking uses `booking.lang`, whoever triggers it (diner, staff, owner,
the waitlist): confirmed, changed, reminder, cancelled, waitlist offer, and the `.ics` text. Every
link in those emails carries the language: the manage link `/b/<token>?lang=<lang>`, the
staff-change fallback `/r/<vid>?lang=<lang>` (`emails._link`), and the waitlist offer
`/r/<vid>?date=...&time=...&party=...&lang=<lang>` (`waitlist._booking_link`). So the page opens in
that language on any device for that tab (rule 4.1 step 1). The redaction regex
(`/[abej]/[A-Za-z0-9_-]+`) stops at `?`, so the token is still removed and only `?lang=pt` stays.

### 4.3 URL strategy [default, D1]

No locale in the path. Routes in `frontend/src/App.tsx` do not change, `isRestaurantRoute` does
not change, Vercel rewrites do not change, existing links in sent emails keep working.
`?lang=xx` is the only URL hook, used by our own emails and by people who want to share a link
in a given language. Rejected: `/pt/...` prefixes (duplicates every restaurant route, touches the
route table and the events/restaurants split, and buys SEO only with server rendering, which we
do not have).

## 5. UX flow per screen, with exact copy

The English copy below is the catalogue's English; Portuguese, Spanish and French are given for
every **new** string. Existing strings keep their English words exactly; their translations live in
the catalogues (samples in 5.6).

### 5.1 Language picker (new; every restaurant page header)

Placement:
- Public pages (`/`, `/restaurants/:slug`, `/restaurants/account`, `/r/:venueId`, `/b/:token`):
  in `PublicHeaderActions`, left of "Log in". `BookingPage` and `ManageBookingPage` gain the same
  `headerActions` (today they have none).
- Owner pages: in `OwnerShell`, at the bottom of the side menu above "Sign out".
- Staff (`/staff/:venueId`, `/owner/:venueId/dashboard`): in the `StaffPage` header actions.
- Phone (under 640 px): inside the existing "Menu" disclosure of `PublicHeaderActions`, as a
  4-button segmented row (each 44 px tall). Owner and staff on a phone: in the same place as on
  desktop (the side menu already stacks).

Desktop control: a ghost button showing a globe icon and the short code, e.g. `PT`. Its
accessible name is the full sentence (below). Activating it opens a small popover list (same
look as the filter chips: white card, lilac hover, purple tick on the current language). Each
option shows the language's own name, with a `lang` attribute so screen readers read it right:
`English` (`lang="en"`), `Português` (`lang="pt"`), `Español` (`lang="es"`), `Français`
(`lang="fr"`). Choosing one switches the page at once (no reload), closes the popover, returns
focus to the button and announces the change in the existing toast region.

Keyboard: Enter/Space opens, arrow keys move, Enter picks, Escape closes and returns focus.
It is a `button` + `role="listbox"` with `aria-activedescendant` (same pattern as the map).

### 7.1 Frontend error rule

`errorMessage(error, fallback)` keeps its signature and output (24 files and their tests call it;
the room editor does not, but nothing outside the migrated files may break). A new sibling
`translatedError(error, t)` in `pages/restaurant/format.ts` is what migrated files call. It reads
`key` and `params` from the **existing** `ApiError.details` (the whole server `error` object), with
runtime checks (`typeof key === "string"`, `key.length <= 64`, `/^[a-z_]+$/`; `params` a plain object
of strings), so `frontend/src/api/client.ts` does not change:
1. a valid key and `errors.<key>` exists in the catalogue -> translated, with the params;
2. else `errors.code.<code>` exists and is specific (`seat_taken`, `hold_expired`, `rate_limited`,
   `network`, `deadline_passed`) -> translated;
3. else the server's `message` (English) — informative beats generic;
4. else the translated fallback `errors.generic` ("Something went wrong. Please try again.").

Lookup uses own-property checks only (`Object.hasOwn`), so a server key like `__proto__` can never
reach a prototype. Params are rendered as text and cut at 100 characters.

### 7.4 Reminders after a language change

Email words are frozen when queued. On `PATCH {lang}`: `drop_reminder` (existing: marks queued
reminders `skipped` and blanks them), then queue the reminder again with key
`booking-reminder-<public_id>-<n>-l<k>`, where `n` is the current change number and `k` is the
number of reminder rows already in the outbox for this booking + 1. The key keeps the
`_reminder_prefix`, so later `drop_reminder` calls still find it; it never collides with an earlier
(skipped) key, even when the diner switches back. Existing keys (`...-<n>`) are not changed.

## 9. Security, privacy and abuse limits

- **No new endpoint, no new external service, no new secret.** Existing per-address rate limits and
  booking caps cover the changed routes.
- `lang` is a closed `Literal` in every request model (`extra="forbid"` stays); `?lang=` values
  outside the released list are ignored.
- `Accept-Language` is parsed only up to 256 characters and 16 entries; it is never logged or
  stored; only the derived 2-letter code is kept on the booking.
- Catalogues are static repository files reviewed in PRs. React renders them as text; no
  `dangerouslySetInnerHTML`. `richText` only maps numbered tags to elements the caller passes.
  In emails, both the translated string and every param are passed through `html.escape`, as today.
- Server-sent error keys are looked up with own-property checks; params are rendered as text and
  cut to 100 characters.
- **GDPR.**
  - *Data minimisation:* we store one 2-letter code per booking/waitlist entry, needed to send the
    emails the diner asked for (Art. 6(1)(b) performance of the booking). No language on accounts.
  - *Retention and deletion:* the code lives on the booking row and follows its existing retention
    and deletion; outbox retention (`scrub_expired`, 30 days) is unchanged.
  - *Browser storage:* `seatplan:lang` in `localStorage` is written only after the person
    explicitly picks a language (or opens a `?lang=` link we sent them). It is a preference the
    person requested, so it falls under the "strictly necessary" exemption of the ePrivacy rules;
    no consent banner is needed. The detected language is never stored.
  - *Transparency:* the privacy text (wherever the restaurant privacy notice lives) gains one
    sentence: "We remember the language you choose on this device, and we keep the language of
    your booking to email you in it." (pt/es/fr in the catalogue).
- **Events isolation:** events routes always render English, so no translated text can leak into
  the events vertical, and the events error bodies have no new fields.

## 13. Rollout

Release switch: build-time variable `VITE_I18N_LOCALES` (not a secret; set in Vercel project
settings and in the e2e frontend server). Default in code: `"en"`, so merging any phase changes
nothing for users until Martim turns a language on. The backend always accepts all four `lang`
values (cheap and harmless).

| Phase | Content | Size |
|---|---|---|
| 0 | `src/i18n` core, provider (forced `en` on events), picker (hidden while only `en` released), design strings, `ApiError.key`, catalogue tests, `noHardcodedText` guard, `docs/i18n.md` | 1.5 days |
| 1 | Discovery + public page + header + cuisine names (pt, es, fr) | 1.5 days |
| 2 | Booking flow + manage page + diner error keys + ambience `phrase_keys` | 2.5 days |
| 3 | `bookings.lang` / `waitlist_entries.lang`, migrate, all diner emails + invite, PATCH lang, demo language mix | 2 days |
| 4 | Staff pages, owner pages, owner code email, owner/room problem codes, Login (owner) | 2.5 days |
| 5 | Room editor strings, **only after Sergio's room-editor work is merged** and with him | 0.5–1 day |
| — | Native review of pt / es / fr catalogues (see D4) | outside dev time |

Deploy order for phase 3: backup the production database, run `python -m app.seed.migrate`
against it, then merge (GitHub Actions deploys on push to `main`). Turn on `pt` first
(`VITE_I18N_LOCALES=en,pt`) after phases 1–3 are reviewed; `es,fr` after their review; staff/owner
ride along once phase 4 is in.

## 14. External services, accounts, cost, legal

None required: no API, no SDK, no account, no secret. The only cost-bearing item is human review
of the translations (D4). Legal: the privacy text sentence in section 9; nothing else changes in
processing purposes. If Martim later wants machine translation of owner descriptions, that would be
a new feature with a provider interface (`TranslationProvider` with a demo "no-op" provider by
default, real provider such as DeepL switched on by `TRANSLATION_PROVIDER` + key in env), a DPA with
the provider, and a note in the privacy text; it is out of scope here.
